# GPT-6 execution guidance

## Verified capability boundary

Reviewed against official documentation on 2026-09-13. GPT-6 Astra introduces asynchronous tool calling, mid-turn steering and reasoning-effort updates that can preserve the prompt prefix. Structured Outputs, compaction and image input are also available capabilities, but are not all new to GPT-6. The model card lists audio and video input as unsupported; use ASR, media tools and extracted frames rather than assuming a raw MP4/WAV is natively understood. Sources: [GPT-6 guide](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra), [model card](https://developers.openai.com/api/docs/models/gpt-6-astra).

This skill configures agent behavior, not the model runtime. Use capabilities actually exposed by the current host. Do not add API fields to Codex tool calls, switch the user's selected model or claim that GPT-6 performs pixel denoising. For a separately requested API implementation, verify the live Responses API contract; async tools need application-managed results using the original call ID, steering uses the documented transport, and configuration updates have compatibility limits.

## Production-specific execution policy

These are workflow choices for this skill:

1. **Continue authorized work.** Carry forward the user's chosen layout, accepted sync difference, exclusion interval and processing scope. A new user message updates those fields instead of erasing completed work. Ask only when missing information materially blocks correctness or an explicit choice is still pending. An already approved plan does not need permission again.
2. **Schedule independent work.** While native PPT rendering or camera processing runs, read the full transcript, finish semantic review or prepare verification inputs. Batch independent reads/probes. Respect dependencies: do not denoise the final crop before layout is settled, or certify a file before encoding and mux complete. GPU jobs may need serialization.
3. **Use tools as available.** Persist process/job IDs and poll with bounded waits; inspect exit code plus measured output. Never interpret a yielded tool call as a finished job. Report meaningful progress in concise Chinese, normally at least once per minute while working, without dumping routine logs.
4. **Keep durable state.** Save a task manifest and decision log under `_work`: input roles/hashes, locked audio stream, user decisions, current plan version/hash, source frame mapping, crop, denoise signature, ASR evidence, completed chunks, running jobs, evidence paths and unresolved checks. After compaction or interruption, read this state and verify actual process/output status before resuming.
5. **Handle steering narrowly.** If the user changes the crop, invalidate crop-dependent denoise/panel/composition checks while retaining eligible ASR and native PPT evidence. If only the cover text changes, update that asset and affected visual checks. Preserve accepted audio unless the user explicitly reopens the audio task. Do not mistake a status question for cancellation.
6. **Structure decisions, measure results.** Author JSON with real numeric values, booleans and absolute frame indexes; convert library scalar types before serialization. Validate geometry, timing and coverage with scripts. Semantic reasons must refer to spoken evidence. Never fill verification fields with a model's guessed PASS.
7. **Bound reasoning and verification.** Spend careful analysis on complete-sermon meaning, uncertain boundaries, motion artifacts and source identity. Routine probes, hashes and encodes are deterministic tool work. If the host exposes adjustable reasoning effort, choose only supported settings; do not hardcode an API-only control or an unsupported level. Once exact-candidate checks pass, rerun only for changes, failures or unresolved evidence.
8. **Delegate only with authority and a useful boundary.** Follow the host/user's delegation policy. If permitted, independent read-only semantic review and technical verification can use separate agents; keep a single owner for the plan, GPU job queue and final promotion. Do not create separate user tasks just to implement internal parallel work.

For skill maintenance, test behavior with concrete scenarios: accepted millisecond offset; new 4K/60 fps input; setup footage followed by reading; processed clips with missing temporal handles; unchanged audio with reusable ASR; a mid-job crop change; failed GPU backend; missing native animation rendering. Expected behavior is precise continuation or a narrowly explained blocker, never silent degradation or a new blanket approval loop. The [official prompting guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices) motivates explicit instruction priority, scoped autonomy and proportionate checks.
